# Magii AirLine サービス概要

## 1. サービス概要

店舗の前で待つ体験をなくす。来店客は店頭のQRを読むだけで列に並び、順番が近づいたら通知を受け取る。店舗側はブラウザの管理画面から呼び出しを1タップで行う。

### 設計方針

- ユーザーにアカウント作成をさせない（QR読み取りから発券まで最短2タップ）
- 一度登録した名前と電話番号は次回以降入力不要
- 店舗スタッフの操作は「次を呼ぶ」に集約する

## 2. 用語

| 用語 | 意味 |
|------|------|
| チケット | 1回の並びを表すレコード。発券から着席・離脱までの単位 |
| 待機番号 | 店舗ごと・営業日ごとの通し番号 |
| 前組数 | 自分より前にいる waiting のチケット数 |
| 呼び出し | 店舗が特定チケットを called に遷移させる操作 |

## 3. ユーザー体験フロー

```
店頭QRを読む
   ↓
[初回のみ] 名前・電話番号を入力
   ↓
「この名前と電話番号を登録しますか？」モーダル
   ↓ はい
待機画面（予想待ち時間 / 待機番号 / 前組数）
   ↓ 順番が来る（プッシュ通知）
呼び出し画面 + [到着しました] ボタン
   ↓
完了
```

2回目以降はQRを読むと登録済み情報が自動で使われ、確認画面から直接発券に進む。

## 4. 画面仕様

### 4.1 ユーザー側（Swift / SwiftUI）

#### U-1 QR読み取り
カメラを起動。QRにはstore_idを含むURLを埋め込む。Universal Linksでアプリが直接起動し、未インストール時はApp Storeへ誘導する。

#### U-2 情報入力（初回のみ）
名前・電話番号・人数を入力。人数は業態次第で省略可。

#### U-3 登録確認モーダル
「この名前と電話番号を登録しますか？」

- [はい、登録する] / [今回だけ使う]

「今回だけ使う」を用意しておくと、他人の端末を借りた場合や登録に抵抗がある人を取りこぼさない。

#### U-4 待機画面（メイン画面）
画面の主役は前組数の巨大な数字。予想待ち時間はその下に副次情報として置く。
Supabase Realtimeで購読し、前の組が進むたびに自動更新する。

#### U-5 呼び出し画面
背景を反転させるなど、待機画面と明確に見た目を変える。番号を大きく表示し、[到着しました] を画面下部の押しやすい位置に置く。

#### U-6 完了画面
短い礼と、次回も使えることの案内のみ。

### 4.2 管理側（Next.js）

#### A-1 ログイン

#### A-2 新規登録（メール＋パスワード）

#### A-3 ダッシュボード

- 現在の待ち組数
- 本日の呼び出し済み / 着席済み / 離脱数
- 待機列一覧（番号・名前・人数・経過時間）
- [次を呼ぶ] ボタン（画面上で最も大きく、常時見える位置に固定）

#### A-4 待ち時間管理
1組あたりの目安時間の設定、一時的な受付停止、手動での順番入れ替え。

#### A-5 顧客管理
来店履歴、no-show履歴の確認。

#### A-6 設定
店舗名、営業時間、QRコードの発行・印刷用ダウンロード

## 5. チケットの状態遷移

```
                  ┌──────────────┐
                  ▼              │
waiting ──▶ called ──▶ seated    │
   │           │                 │
   │           └──▶ no_show ─────┘（再呼び出し可）
   ▼
cancelled
```

| 状態 | 説明 | 遷移させる主体 |
|------|------|----------------|
| waiting | 待機中 | 発券時 |
| called | 呼び出し済み | 店舗 |
| seated | 着席・対応完了 | 店舗（またはユーザーの到着ボタン起点） |
| no_show | 呼び出しに応答なし | 店舗 |
| cancelled | ユーザーが辞退 | ユーザー |

> **要検討** — [到着しました] を押した時点を seated にするか、arrived を追加してスタッフの確認を待つか。飲食店なら席の準備があるので arrived を挟むほうが実態に合う。

## 8. デザインシステム

参考画像から抽出。純黒背景、濃灰カード、白のプライマリボタンという3層構成。

### カラー

| 用途 | 値 |
|------|-----|
| 背景 | #000000 |
| カード面 | #1A1A1C |
| カード面（副） | #242426 |
| 主テキスト | #FFFFFF |
| 副テキスト | #8E8E93 |
| 罫線 | #2C2C2E |
| プライマリボタン背景 | #FFFFFF |
| プライマリボタン文字 | #000000 |
| 進行中アクセント | #32D74B |
| 警告・no-show | #FF453A |

アクセントは緑1色に絞る。呼び出し中だけ配色を反転させ、通常時との差を最大化する。

### タイポグラフィ

| 役割 | 指定 |
|------|------|
| ヒーロー数値 | SF Pro Display Bold, 72–96pt, tracking -2% |
| 見出し | SF Pro Text Semibold, 20pt |
| 本文 | SF Pro Text Regular, 15pt |
| ラベル | SF Pro Text Medium, 13pt, #8E8E93 |

数字を主役にするレイアウトなので、桁数が変わってもガタつかないよう等幅数字（monospacedDigit）を指定する。

### コンポーネント

- カード角丸 20pt、カード間の余白 12pt、画面左右マージン 16pt
- プライマリボタンは全幅のピル型、高さ 56pt
- 進捗バーは高さ 4pt、両端丸め
- 影は使わない。面の明度差だけで階層を表現する

### ライティング

ボタンは動作をそのまま書く。「送信」ではなく「順番をキャンセル」「到着しました」。呼び出し画面の文言は短く、○○様、席のご用意ができました のように主語を明確にする。

## 9. 技術構成

```
iOS       : Swift / SwiftUI
管理画面   : Next.js / TypeScript
バックエンド: TypeScript（Supabase Edge Functions）
DB / 認証  : Supabase（Postgres + Auth + Realtime）
通知       : APNs
```

- 読み取りはSupabase直結、書き込みはバックエンド経由
- RLSは最初のテーブルから有効化する。tickets にクライアント用のINSERT/UPDATEポリシーは作らない
- 型は supabase gen types typescript で生成し、バックエンドと管理画面で共有

## 10. 未決定事項

着手前に埋めるべき項目。上ほど優先度が高い。

### 1. 本人識別の方式
アカウントを作らせない以上、「次回から入力不要」をどう実現するかを決める必要がある。端末のKeychainにUUIDを保存し guests.device_id と突き合わせる方式が第一候補。Supabaseの匿名認証を使う手もある。機種変更で履歴が消える点は許容する前提で良いか。

### 2. 電話番号の扱い
個人情報にあたる。取得目的（SMS送信するのか、店頭で呼ぶためだけか）、保持期間（営業日終了後に削除するか）、削除手段をプライバシーポリシーとあわせて決める。SMSを送らないなら、そもそも電話番号は不要かもしれない。

### 3. 業態
飲食店（人数と席数のマッチングが必要）か、クリニックや役所（順番の追い越しが発生する）かで、party_size の要否と管理画面の作りが変わる。

### 4. 「AIR」の定義
サービス名なのか、店舗内の特定の列を指すのか。命名なら、画面文言とQRのドメインに関わるため早めに確定させたい。

### 5. 呼び出し後の猶予
何分応答がなければ no_show にするか。自動にするか手動のみか。

### 6. 通知のタイミング
「あと2組」で予告通知を出すか、呼び出し時のみか。予告を出すなら遅延実行の仕組みが必要になる。

## 11. 分担とマイルストーン

| 担当 | 範囲 |
|------|------|
| A | SwiftUI全画面、Realtime購読、APNs受信、QR読み取り |
| B | DBスキーマ、RLS、Edge Functions、採番の排他制御 |
| C | Next.js管理画面、通知送信、スケジューラ |

### マイルストーン

- **M1** スキーマとRLS確定、発券と呼び出しがAPIで動く
- **M2** iOSで発券から待機画面まで通し、管理画面から呼び出せる
- **M3** プッシュ通知、no-showとキャンセル、実店舗を想定した通しテスト
- **M4** ダッシュボードの集計、設定画面、QR発行

> BとCの境界を先に握っておく。通知の送信処理をEdge Functions側に置くのか、管理画面の操作を起点にするのかが曖昧だと必ず衝突する。
